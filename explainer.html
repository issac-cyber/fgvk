fgvk — 瀏覽器影片的即時插幀

把瀏覽器視窗裡 24/30/60fps 的影片，用 lsfg-vk 即時插成 ~2× 幀率，顯示在同一塊螢幕上。音頻照舊由瀏覽器播放。
Ubuntu 26.04 GNOME Wayland 2× AMD R9700（各帶一屏 3440×1440） C++20 SDL3 + Vulkan 1.2 + PipeWire lsfg-vk 2.0.0 本機個人用・不分發

⚡ 30 秒理解

你在瀏覽器看影片（24fps）。這台機器裝了 Steam 的 Lossless Scaling 的 lsfg-vk Vulkan layer——它能在兩幀之間「算」出中間幀（插幀）。fgvk 做的事就是把一條觀看路徑自組起來：

1
抓畫面：用 XDG portal + PipeWire 高率捕捉「瀏覽器視窗」的原始畫面（不截屏、無缩放失真）。
2
去重：相同的幀（24fps 影片會有大量重複幀）不送進插幀器，省 GPU、也避免插出鬼影。
3
呈現：用自己的 Vulkan 全螢幕視窗播放這些幀。
4
插幀：lsfg-vk 作為 implicit layer「寄生」在 present 階段，每兩幀之間插入生成幀 → 螢幕以 ~2× 速率刷新（165Hz 螢幕 + 2× = 最多 120 帧/秒）。
聲音完全不走這套管線——瀏覽器自己播，插幀視窗是靜音的（音畫偏移約 1–2 幀，設計上接受）。

專案有四個同層組件：screen-fg（主 binary）、screen-fg-gui（桌面 GUI 控制器）、shared/（兩端共用的協議 header）、specs/（鎖定版設計文件）。

階段 ①捕捉：XDG portal + PipeWire

GNOME Wayland 下，任何程式都不能直接抓螢幕/視窗——mutter 把一切擋在 XDG portal 後面。所以要走 portal 的 ScreenCast 介面：它會彈出標準選窗對話框，授權後用 PipeWire 收原始畫面 buffer。

流程（Capture::start()，阻塞到使用者選完）

1
g_bus_get_sync 取得 session bus 連線 → org.freedesktop.portal.Desktop
2
CreateSession（必須帶 handle_token + session_handle_token，否則 portal 1.21.1 會 crash）
3
SelectSources → GNOME 標準 picker 對話框彈出，使用者選「瀏覽器視窗」（每次啟動重選、不 cache 授予）
4
Start → 拿到 stream 權限
5
OpenPipeWireRemote → 收到 PipeWire 的 fd → 以 client API 收 per-frame buffer（event-driven，上限 60fps）

為什麼這樣設計

決定理由
window target（不是整屏）消滅「抓到 FG 自己的輸出視窗」的回饋迴路（插幀視窗自己蓋住螢幕 → 抓到的是插幀結果 → 無限套娃）
60fps 上限、砍掉 >60Hz 捕捉2× 60 = 120fps ≤ 165Hz 螢幕放得下；>60fps 內容 2× 也放不開，無價值（決策 Q1）
每次啟動重跑 picker、不 cacheportal 授予會失效，cache 容易拿到過期 session（Q5）
buffer 是 1:1 紋理無 scaling、無 dithering、游標隱藏、BGRA 與螢幕同格式 → 品質保真
深入：GDBus 呼叫的具體方式

用 GLib 的同步 API：g_bus_get_sync 拿連線、g_dbus_connection_call_sync 發呼叫（async signal 用 onSignal 回調等 picker 結果）。PipeWire 主迴圈跑在獨立交替線程，主迴圈的 poll() 負責保持 DBus 連線健康。isDead() 偵測「來源視窗被關 / 串流斷掉」→ 工具自動退出（Q9）。

階段 ②去重：32×32 luminance grid + MAD

24fps 影片在 60fps 捕捉下，每 2.5 張捕捉幀才真正變一次——其餘全是重複幀。把重複幀丟掉，插幀器才不會白做工（也不會在兩張相同幀之間插出鬼影）。這一步全在 CPU做、零 GPU 佔用。

算法（Deduplicator）

1
把整幀 raw BGRA 降採樣成 32×32 的亮度（luminance）grid（1024 個格子）
2
跟上一幀的 grid 算 MAD（mean absolute difference，平均絕對差）
3
MAD < 3.0/255（config 可調）→ 視為重複、丟掉；否則送進呈現
4
第一幀永遠呈現（沒有「上一幀」可比）

為什麼選這個方案（vs 其他）

方案結果原因
全 buffer 嚴格相等❌ 不採編碼壓縮噪聲讓兩張「看起來一樣」的幀永遠不相等
全 buffer hash + 閾值❌ 不採8MB 全讀太慢太脆
GPU compute pass❌ 不採多一段同步沒必要
CPU 32×32 grid + MAD✅ 定案對壓縮噪聲穩健；1080p 約 1–2ms；零 GPU 佔用（Q2）
結果：VFR 安全（只呈現「真的變了」的幀）。副作用提醒：合成測試幀的 16×16 移動方塊太小（佔全幀 ~0.03%），格化後 MAD ≈ 0.001 < 3.0 → dedup 只放行第一幀，所以 e2e 輸出是「3 帧捕捉 / 1 帧呈現」。

階段 ③呈現：SDL3 全螢幕 + Vulkan FIFO swapchain

把去重後剩下的幀，用自己的 borderless 全螢幕視窗、以 Vulkan 播放。這支視窗就是「被 lsfg-vk 插幀」的目標。

buffer 流程（每幀）

1
PipeWire 送來的 BGRA 幀（CPU 端 copy）→ 寫進 CPU upload buffer
2
copy 到 staging image（依 swapchain 尺寸建立）
3
blit（scale）到 swapchain image
4
選配畫上 HUD 文字（FPS / 倍數 / profile / Hz）
5
vkQueuePresentKHR（FIFO 模式）→ layer 就是 hook 在這一步插生成幀

關鍵決定

項目決定備註
swapchain 模式VK_PRESENT_MODE_FIFOlayer 會強制；VRR 要關（研究 02 結論）
buffer 導入CPU 上傳（非 dmabuf zero-copy）建置偏離：spec 原案是 dmabuf import，實作走 CPU 上傳（§13）
imageUsage必須含 TRANSFER_SRC + TRANSFER_DST只給 COLOR_ATTACHMENT 會 let blit 變非法 GPU 操作（layer 要讀 swapchain 幀）
GPU 選擇跟 display 的 card 走；config 可用 PCI bus ID 強制本機 2 張 R9700 各帶一屏（Q7）
延遲2× FG 端到端 ≈ 17–35msFG compute ≲1–2ms + FIFO 排隊 1–2 VBlank；接受 ~2 幀音畫偏移
深入：本機 Vulkan 環境的特殊性

Mesa 26.0.8 radv + SDL3 0.4.2 + Wayland。Vulkan 只 enumerate 到 1 個 device（雖有兩張卡），GPU 選擇無歧義。本機 Vulkan header 是裁剪版：例如 vkResetCommandBuffer 沒有 device 參、VkImageSubresourceRange 沒有 image 成員（image 在 barrier 本體上）、vkCmdCopyBufferToImage 第 4 參是 dstImageLayout——寫 code 時對照官方文件會踩錯。

階段 ④插幀：lsfg-vk implicit layer

插幀算法本身是 Steam Lossless Scaling 的 lsfg-vk——一個 implicit Vulkan layer。它「寄生」在應用程式的 instance/device/present 呼叫上，不需要應用自己呼叫任何 API。screen-fg 只要讓層「認得」自己，插幀就自動發生。

怎麼讓 layer 認得 screen-fg

1
layer 裝在 ~/.local/share/vulkan/implicit_layer.d/（implcit layer 目錄，Vulkan loader 自動載入）
2
~/.config/lsfg-vk/conf.toml 裡有一支 [[profile]]，其 active_in = ["screen-fg"]——依執行檔名匹配
3
匹配成功 → layer 初始化（half precision）、hook present → 每兩幀插 1 幀生成幀（預設 profile「2x FG / 100%」）
這個「依執行檔名匹配」的機制正是暫停功能的鑰匙：執行檔名不匹配 → layer 自我 unload → 同樣的程式變成「純呈現、無插幀」。詳見下一節的 re-exec 機制。

shader 來源（授權）

插幀的 compute shader 來自使用者已購買的 Steam app（Lossless Scaling）的 lsfg-vk update channel——官方作者分支的 build 直接 ship 相容的 2.1MB lsfg-vk.dll（PE 檔 .rsrc 內數字 resource ID 1–26 對應 v3.1 shader 集合）。授權 CC BY-NC-ND 4.0：本機個人用 OK，不可分發、不可改作。screen-fg 啟動時會健康檢查（層是否 enumerate 到、profile 是否匹配），不匹配 → 明確警告、不靜默降級。

深入：為什麼不走 B 方案（direct API）

lsfg-vk 也有 v2 public API（lsfgvk::Instance/Context、OPAQUE_FD 的 source/destination/sync fd、timeline semaphore），可以直接呼叫、不需 layer 與 .NET runtime。但 spec 定案（Q3）：A（layer hook）預設——已裝好、零額外同步代價；B 作為文件化 fallback（切換條件：profile 匹配失敗 / 某些視窗模式 hook 不到 / 要更低延遲 / 便攜性）。

🔌 stdio 控制協議（GUI ⇄ screen-fg）

GUI 是 parent、screen-fg 是 child。兩條管線：命令走子程序 stdin（行式純文字）、狀態走 stdout（JSON 行）。screen-fg 的 stdout 只有協議 JSON 行、log 全走 stderr（GUI 收進 log 區）。協議的單一來源是 shared/protocol.hpp——兩端編同一份 header，缺欄/格式錯 → nullopt（明確跳過、不默默 default）。

⏸️ 暫停/恢復 = re-exec（最反直覺的一塊）

「暫停」的語義（Q8a）= 停止插幀、但繼續呈現原始幀（還看得到瀏覽器在動，只是沒插幀）。為什麼不能運行中直接把 layer 關掉？因為 lsfg-vk layer 是 per-process 全域單例、config 初始化只讀一次——跑起來就切不了。解法很土但有效：把程式重新 exec 成一份「layer 認不得」的複製本。

機制（re-exec 流程）

1
啟動時 ensurePlainCopy：把 screen-fg cp 成 screen-fg-plain（同目錄、真檔案非 symlink——/proc/self/exe 會被 kernel 解析 symlink，symlink 改變不了 layer 的辨識結果；每次都重做，build 更新後舊 copy 會過期）
2
收到 pause（或 P 鍵）→ 純函數 resolveReexec() 決定 plan：target = screen-fg-plain、env SCREENFG_STATE=paused、SCREENFG_HUD 帶上當前 HUD 狀態
3
setenv + execv（PID 不變、argv 帶過、跳過 --passthrough 避免無限 re-exec）
4
複製本啟動：執行檔名 screen-fg-plain 不匹配 conf.toml 的 active_in → layer 自我 unload → 純呈現、無插幀。程序重跑完整啟動（含 source->start()）
5
resume（或 P 鍵）→ 反向 re-exec 回 screen-fg、env SCREENFG_STATE=normal → layer 重新認得 → 插幀恢復
代價（已知、有提示）：re-exec 重跑 source->start() → 真實捕捉模式下 XDG portal picker 會重跑（要重新選窗）；synthetic 模式看不到此現象。GUI 的暫停鈕 tooltip + log 都有警告。
詞彙陷阱：re-exec env 用 "normal"/"paused"；status JSON 用 "running"/"paused"/"exiting"。兩套不同詞彙，code 裡有明確註解警告不可混用。

🖥️ GUI 控制器（screen-fg-gui）

一個 GTK4（gtkmm-4.0）桌面 app，parent 身份 fork+exec 出 screen-fg child，握住三條 pipe（stdin 寫命令 / stdout 讀 status / stderr 讀 log），用按鈕操作。不改 screen-fg 的 LOCKED 管線、CLI 完整保留並存。

主窗戶（560×640，App ID com.issac.screenfg-gui）

控件行為
binary 路徑 Entry自動偵測（順序：$SCREENFG_BIN → build/screen-fg → ../screen-fg/build/screen-fg → /usr/local/bin → 執行檔相鄰 → PATH 掃描）；全找不到顯示提示、擋住啟動
啟動/停止鈕狀態機：未 running → fork+exec（狀態 "starting…"）；running → 送 quit 命令（異步退出）
狀態列即時顯示 FPS / 倍數 / layer on-off / state（running/paused/exiting → 已停止、錯誤結束 (N)）
暫停/恢復鈕標籤跟 state；按下發 pause/resume；tooltip + log 警告會重跑選窗
HUD switch發 hud 1|0（立即生效）
log 區child stderr 逐行 + GUI 端事件

process 控制（process.cpp）

fork 前開三條 pipe；child dup2 後 execv。父端起 兩個 reader 線程：stdout reader（poll 100ms 超時 + 8KB chunked read + 抽行 → 純 protocol::parse → 回調排回 GLib 主執行緒）、stderr log reader（同模式）。EOF 時收屍（waitpid，被 signal 殺回 128+sig）並補發 exit 回調。

退出不可卡死：destructor 先送 quit → 設 stopping_ 讓 reader ~100ms 內退出（bounded join）→ 關 stdin（child EOF）→ waitpid(WNOHANG)；child 還活就 SIGTERM 確保收掉（否則 orphan 給 init）。舊 code 阻塞 join() 會卡幾分鐘的教訓。

安裝：binary 進 PATH 後 cp screen-fg-gui.desktop ~/.local/share/applications/（圖示：Name[zh_TW]="screen-fg 插帧控制"、Icon=video-display、Categories=Video）。

🩺 健康檢查與 clamp（不靜默降級）

啟動時（screen-fg 依序）

檢查方法失敗時
layer 存在vkEnumerateInstanceLayerProperties 找 VK_LAYER_LSFGVK_frame_generation警告（檢查 implicit_layer.d）
profile 匹配讀 ~/.config/lsfg-vk/conf.toml 找 active_in 含 "screen-fg" 的 profile警告（layer 會自我 unload、FG 不會啟動）
VRAM 餘量讀 /sys/class/drm/cardN/device/mem_info_vram_total|usedfree < 2048 MB → 警告（可能有其他程序佔 GPU，非 OOM crash）

倍數 clamp（Q4）

maxMult = floor(displayHz / 60)（window 捕捉上限 60fps）。例：165Hz → 2x（2×60=120 ≤ 165 ✓）；120Hz → 2x；119Hz → 1x。若 content_fps_cap < 60（如 30fps 內容）→ 再依它 clamp 並明確警告。超顯示能力的 4× 請求不會發生——自動 clamp 到放得下的最大值。
